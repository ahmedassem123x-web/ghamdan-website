## Root cause (diagnosed 2026-11-14 ~06:30–06:38 UTC)
The exec sandbox is in a degraded state since ~06:24 UTC (coinciding with a Chromium renderer
OOM crash and a browser SIGTRAP launch crash; shared VM memory 137–256 MB free of 7934 MB):

**Any process that ingests content from a file on the workspace overlay — or piped data
derived from workspace files — becomes permanently unable to write regular files**
(`write()` → EPERM) for the rest of its lifetime. Pipe/stdout writes still work; the taint
does not expire (30 s sleep test: still EPERM).

Evidence:
- `node`: read `/tmp/ipc-child.js` → write OK. Read ANY workspace file (even `package.json`,
  even a 15 KB `node_modules/next/dist/...js`) → subsequent writes to /tmp AND workspace FAIL.
- cwd, file size (100 B–100 KB), and target path do not matter. `readFileSync` alone poisons.
- `cat workspace-file | tee /var/tmp/dest` FAILS (tee never read a workspace file, but the piped
  data came from one). `echo "clean" | tee /var/tmp/clean.txt` WORKS. Same for GNU tar and
  Python tarfile extracting a workspace-sourced archive (even across separate exec calls via a
  named pipe) — the consumer of workspace-derived data cannot write files.
- `cp`, `cat > dest`, `tsc --noEmit` (tsbuildinfo write) all fail intermittently with EPERM.
- The trace-reporter EPERMs (`.next/trace`, `~/.config/nextjs-nodejs/config.json.*`) are
  NON-FATAL red herrings (that code catches its own write errors). The fatal write is a
  different one the preload traces could not intercept.

This is an environment/sandbox problem, NOT a code problem. Builds succeeded at 05:52, 06:05
and 06:17 UTC before the degradation.
